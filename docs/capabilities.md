# Support and verification levels

`rvg.capabilities()` (or `rvg capabilities`) returns the same content as a static table in the code. For every row of this document that has a status word, that table has an entry with the same status, and a test (`tests/packaging/test_capability_table.py`) compares the two tables. For the rows of policy keys, the table also returns the value it reads from the policy file (`policy_defaults`). What is guaranteed and what is traded (measured numbers and evidence) is in [Guarantees and trade-offs](GUARANTEES.md). A status is the **strongest recorded evidence**, written with where that evidence came from. A component that is not implemented is not replaced by another component; it stays `NOT_IMPLEMENTED`.

The Korean original is [capabilities.ko.md](capabilities.ko.md). This English text is canonical; the test reads both, and both carry the same numbers (`scripts/check_doc_numbers.py`). Experiment IDs and "private research repository report `docs/…`" name reports of the private research repository in which RVG was developed; those reports are not public.

Status vocabulary: IMPLEMENTED (code exists) · TESTED_OFFLINE (deterministic, mock or replay tests) · TESTED_REAL_BACKEND (conformance tests on a real DB service) · TESTED_LIVE (real model calls) · ADOPTED (product default) · ADOPTED_OPT_IN (adopted but off by default, turned on explicitly) · EXPERIMENTAL / EXPERIMENTAL_ARM (turned on only in the evaluation runner) · NOT_IMPLEMENTED.

## Known limits (not deleted)

- N1: with the resident index, the candidate stage and `layout: rebuild`, every stamp (document or revocation change) regenerates the whole matrix (about 53 s for 100k JSON vectors); the first query pays a cold cost; generation races when several processes use the same store are prevented by leases and fencing, but the cost remains.
- N3: `current` (the default up to dev26) does not release when the knowledge number changes while the answer is made. Under a load of continuous concurrent writes, releases fall to almost 0 (a finding of the research repository's N3L). The dev27 default (scoped) releases when the change is unrelated to what the answer read.
- U24 (dev27): the default release check uses the state store's outbox, ACL, revocation and document reads (the SQLite and PostgreSQL state stores have them). In a custom store without them, the change becomes UNKNOWN and the answer is held (safe side, availability loss). In the evaluation runner it can be compared with the arm `release.mode = current`; the product rollback is the dev26 wheel. A regeneration after a related change can add one generation call per request (U24 live related changes: Haiku +97 per 100 requests). Under churn, `acl_moved_during_check` holds remain since dev42 (U32) only for ACL rows that touch a document or family the answer read (holds under unrelated changes 32 → 0). If the state store does not provide `Release.hidden`, the answer is held as before.
- N2: when the revision relation is uncertain, the prior replaces the old version — 1 assertion remains in synthetic conflict cases (kept because its accuracy on real revisions is higher than that of the rejected alternative).
- Every provider result is the result of that model combination. Replacing it (with a local judge, for example) needs a new evaluation.
- The extraction is a behaviour-preserving copy. It does not newly certify correctness, security or local execution.
